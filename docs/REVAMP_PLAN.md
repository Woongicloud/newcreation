> 상태: 0–4단계 구현 완료, 배포(Supabase·Railway·Vercel) 재연결 완료. 실기기 리허설이 남음 → [REHEARSAL.md](REHEARSAL.md) · 작성일 2026-11-11
> 범위: 진행자 리모트 추가, 중간 개인 집계, 관리자 표시 설정, 포인트 체계 간소화, 학년·브릿지 팀 구성, 최종 시상 세트

## 1. 개편 방향 요약

기존 3-way 구조(참가자 폰 · 관리자 PC · 프로젝터 Display)에 **진행자 리모트**를 더해 4-way 구조로 간다.

| 화면 | 경로 | 기기 | 역할 |
|---|---|---|---|
| 참가자 | `/` `/lobby` `/game` | 개인 폰 | 이름·학년·브릿지 등록, 답안 입력, 채팅, 내 점수·순위 확인 |
| Display | `/display` | 프로젝터 | 문제·타이머·집계·시상 송출 |
| 관리자 | `/admin` | PC (음향/방송석) | 방 생성, 문제 세트 업로드, 표시 설정, 모니터링, 시상 |
| **진행자 리모트 (신규)** | `/host` | 진행자 폰 (강단) | 게임 순서 진행, 정답 공개, 집계 송출 |

기술 스택(React 18 + Vite + Tailwind + Zustand / Express + Socket.io / Supabase)은 유지한다.
게임 모드 컴포넌트 11종은 재사용하고, **서버 진행 로직 · 점수 엔진 · 관리자/Display 페이지**는 새로 짠다.

### 지금 구조에서 개편 때 같이 정리할 문제

현재 코드를 읽으며 확인한 것들로, 신규 요구사항과 직접 얽혀 있어 함께 처리한다.

- **관리자 비밀번호가 클라이언트 번들에 포함됨** — `VITE_ADMIN_PASSWORD`가 빌드 결과물에 그대로 들어가 누구나 볼 수 있다 (`client/src/pages/AdminPage.jsx:6`). 진행자 기기가 추가되므로 서버 발급 토큰 방식으로 바꾼다.
- **진행 상태가 서버 메모리에만 있음** — Railway 재시작 시 진행 중인 방이 사라진다 (`server/gameEngine.js`).
- **진행 명령에 순서 보호가 없음** — `admin:next_question`이 중복 수신되면 문제가 건너뛰어진다. 관리자 PC와 진행자 폰 두 곳에서 조작하게 되면 더 자주 발생한다.
- **채팅 로그가 세션과 연결되지 않음** — `session_id: null`로 저장된다 (`server/chatHandler.js:22`).
- **채팅 폰트 크기가 서버에서 난수로 결정됨** — 조절하려면 구조를 바꿔야 한다 (`server/chatHandler.js:8`).
- **Display 색상·폰트가 하드코딩** — 테마 선택을 하려면 토큰화가 필요하다 (`client/src/pages/DisplayPage.jsx`).
- **페이지가 단일 파일에 몰려 있음** — AdminPage 786줄, DisplayPage 669줄.

## 2. 핵심 설계

### 2.1 서버: 단일 상태 머신 + 역할별 상태 전송

방(room)마다 하나의 진행 상태를 서버가 소유하고, 모든 화면은 그 상태를 받아 그리기만 한다.

```
lobby → round_intro → question_open → question_closed(정답 공개)
                           ↑                  ↓
                           └──── 다음 문제 ────┤
                                              ↓
                     standings(개인 집계) ⇄ round_end → … → final → awards
```

- 서버는 상태가 바뀔 때마다 `room:state` 스냅샷을 내보내되, **역할에 따라 내용을 다르게** 보낸다.
  - 참가자: 정답 제외, 본인 점수·순위만
  - Display: 문제·타이머·제출 현황·집계
  - 진행자/관리자: 정답, 다음 순서 미리보기, 제출 현황, 접속자 수
- 재접속 시 같은 스냅샷 한 번으로 화면이 복구된다 (현재의 이벤트별 개별 복구 로직 제거).
- 타이머는 매초 tick 이벤트 대신 **마감 시각(`deadlineAt`)** 을 한 번 보내고 각 화면이 계산한다. 서버가 마감만 판정한다.
- 상태 스냅샷은 전환 시점마다 Supabase에 저장해, 서버가 재시작돼도 방을 복구한다.

### 2.2 진행 명령과 중복 방지

진행자와 관리자는 같은 명령 채널을 쓴다.

```js
socket.emit('host:command', { type: 'next', step: 17 })
```

- `step`은 현재 진행 단계 번호. 서버의 현재 값과 다르면 명령을 무시한다 → 더블 탭이나 두 기기 동시 조작으로 문제가 건너뛰어지지 않는다.
- 명령 종류: `next` `reveal` `show_standings` `hide_standings` `pause` `resume` `extend_time` `skip` `goto` `end_game` `award_next` `award_step` `show_main`

### 2.3 인증

- `/admin` 로그인: 비밀번호를 서버로 보내 검증 → 서명된 토큰 발급 (role: admin). 클라이언트 번들에 비밀번호를 두지 않는다.
- `/host` 접속: 관리자 화면이 방마다 **진행자용 QR/링크**를 발급 (role: host, 해당 방 한정). 진행자는 비밀번호 입력 없이 QR로 들어온다.
- 모든 소켓은 연결 시 토큰으로 역할을 확정하고, 이후 이벤트마다 비밀번호를 싣는 현재 방식은 없앤다.

| 권한 | admin | host |
|---|---|---|
| 방 생성/종료, 문제 세트 업로드, 참가자 수정 | ✅ | — |
| 표시 설정 (폰트/테마/배경), 시상 세트 편집 | ✅ | — |
| 게임 진행 (시작/다음/정답 공개/건너뛰기/일시정지/게임 종료) | ✅ | ✅ |
| 집계 송출 | ✅ | ✅ |
| 시상 진행 | ✅ | ✅ |
| Display를 메인 화면으로 전환 | ✅ | ✅ |

리모트는 설정·준비 작업 없이 **게임 흐름 전체를 조작하는 용도**로만 쓴다.

## 3. 요구사항별 설계

### 3.1 진행자 리모트 UI (`/host`)

강단에서 한 손으로, 화면을 오래 보지 않고 조작하는 것을 기준으로 한다.

```
┌──────────────────────────┐
│ R2 초성 퀴즈 · 3/8   ● 연결됨 │  ← 현재 위치, 연결 상태
├──────────────────────────┤
│ 문제: ㅂㄷㄹㅎ              │
│ 정답: 베들레헴              │  ← 진행자에게만 보임
│ ⏱ 12초   제출 34/41       │
├──────────────────────────┤
│                          │
│      [   정답 공개   ]     │  ← 주 버튼 1개, 상황에 따라 라벨 변경
│                          │
├──────────────────────────┤
│ 다음: 문제 4 "ㅇㄹㅅㄹ"      │  ← 다음 순서 미리보기
├──────────────────────────┤
│ [개인 집계] [일시정지] [⋯]   │  ← 보조 동작
└──────────────────────────┘
```

- **주 버튼 하나**가 현재 단계에 맞는 다음 동작을 수행한다: 게임 시작 → 문제 시작 → 정답 공개 → 다음 문제 → 라운드 결과 → 다음 라운드.
- 보조 동작: 개인 집계 송출/닫기, 일시정지, 시간 연장(+10초), 문제 건너뛰기, 순서표에서 특정 문제로 이동.
- 게임이 끝나면 같은 주 버튼으로 시상을 진행한다 (→ 3.6).
- **메인 화면 띄우기** 버튼: 시상이 끝난 뒤(또는 필요할 때) Display를 메인 화면(행사 타이틀 + 배경)으로 돌린다. 시상 결과가 계속 떠 있지 않게 마무리하는 용도.
- 건너뛰기·게임 종료 같은 되돌릴 수 없는 동작은 확인 단계를 둔다.
- 화면 꺼짐 방지(Wake Lock), 연결 끊김 시 화면 상단 경고 + 자동 재접속 후 상태 복구.
- 관리자 PC의 진행 패널도 같은 컴포넌트를 써서, 진행자 폰이 없어도 PC만으로 진행할 수 있다.

### 3.2 게임 중간 개인 집계

- **송출 시점**: 진행자가 문제 사이 언제든 `개인 집계` 버튼으로 띄우고 닫는다. JSON에서 라운드에 `"standingsAfter": true`를 주면 라운드 종료 시 자동으로 띄운다.
- **Display**: 상위권을 순위순으로 나열하고 **자동 스크롤**한다.
  - **상위 10명까지만** 점수와 함께 노출한다 (`standingsTop`, 기본 10). 11위 이하는 Display에 나오지 않는다.
  - 10위에서 시작해 1위까지 올라가며 자동 스크롤하고, 끝나면 잠시 멈춘 뒤 반복
  - 한 줄당 표시 시간 고정, 관리자 설정에서 배속 조절
  - 각 줄은 **`등수 · 학년 · 브릿지 · 이름 · 점수`** 순서로 나열한다. 예: `3  중2  브릿지 B  김하늘  1,250`
- **참가자 폰**: 집계가 떠 있는 동안 본인 순위와 점수를 크게 보여준다. 10위 밖 참가자도 자기 순위는 폰에서 확인한다.
- **집계 범위**: 누적(기본) / 이번 라운드만 — 진행자가 전환.
- 중간 집계는 **개인 랭킹만** 출력한다. 학년·브릿지 순위는 최종 시상에서 공개한다 (→ 3.6).

### 3.3 관리자 페이지 — 표시 설정

`/admin`을 탭으로 재구성한다: **준비**(방·문제 세트·진행자 QR) / **진행**(리모트와 동일 패널 + 모니터링) / **표시 설정** / **시상**.

표시 설정은 방 상태에 `displaySettings`로 저장하고, 바꾸는 즉시 Display에 반영한다.

| 설정 | 조작 | 비고 |
|---|---|---|
| 채팅 폰트 크기 | 슬라이더 (50%–300%) | Display에서 CSS 변수로 배율 적용. 서버 난수 크기는 제거하고 메시지별 편차만 클라이언트에서 소폭 부여 |
| 채팅 표시 | 켜기/끄기, 투명도, 흐르는 속도 | 문제 풀이 중 자동 숨김 옵션 |
| 테마 | 프리셋 선택 (다크 네온 / 파스텔 / 라이트 등) | 색·폰트를 CSS 변수 토큰으로 정의 |
| 배경 | 단색 / 그라디언트 / 이미지 / 영상 | 관리자 화면에서 업로드 → Supabase Storage에 저장, 올려둔 파일 목록에서 선택. URL 직접 지정도 가능 |
| 집계 스크롤 속도 | 0.5×–2× | |

- 설정 화면에 Display 미리보기를 축소해 넣어, 프로젝터를 보지 않고도 확인할 수 있게 한다.
- 문제용 이미지·오디오도 같은 저장소에 올려 JSON에서 URL로 참조할 수 있다 (현재는 리포의 `client/public/media/`에 넣고 재배포해야 함).
- 설정은 세션에 저장되며, "기본값으로 저장"으로 다음 방에도 이어 쓸 수 있다.
- JSON 문제 세트에서 `"display": { "theme": "pastel", "background": "/media/bg.jpg" }`로 초기값을 줄 수 있다.

### 3.4 포인트 간소화

**변경 전**: `maxScore × (0.3 + 남은시간비율 × 0.7)`, 오답도 시간 비례 감점 (`server/scoringEngine.js`).
**변경 후**: 시간은 점수에 영향을 주지 않는다. 맞으면 지정 점수, 틀리면 지정 감점. 라운드마다 손실 한도를 자동으로 걸어 점수가 과하게 깎이지 않게 한다.

```json
{
  "sessionName": "11월 레크레이션",
  "scoring": { "points": 100, "penalty": 0 },
  "rounds": [
    {
      "roundNumber": 1,
      "theme": "성경 상식",
      "gameMode": "multiple_choice",
      "points": 100,
      "penalty": 50,
      "standingsAfter": true,
      "questions": [
        { "content": "…", "choices": ["…"], "correctAnswer": "…", "timeLimit": 15 },
        { "content": "보너스 문제", "choices": ["…"], "correctAnswer": "…", "points": 300 }
      ]
    }
  ]
}
```

**규칙**

1. 점수 값은 `문제 → 라운드 → 세트(scoring) → 기본값(5 / 0)` 순으로 찾는다. (8장: 점수 단위 변경)
2. 정답 `+points`, 오답 `-penalty`, 미제출 0점.
3. **손실 한도**: 한 참가자가 한 라운드에서 잃는 합계는 **그 라운드 전체 문제의 감점 합의 50%** 를 넘지 않는다. 넘는 부분은 반영하지 않는다. 서버가 자동 계산하므로 JSON에 따로 적지 않는다.
   - 예: 감점 50점 × 8문제 = 400점 → 그 라운드에서 최대 200점까지만 깎인다. 5번째 오답부터는 감점 없음.
   - **누적 계산**: 문제마다 `penalty`가 그 문제의 최대 손실이고, 오답이 쌓이며 감점 누계가 한도에 닿으면 그 뒤로는 깎이지 않는다. 정답으로 얻은 점수와 상계하지 않는다.
   - 비율을 바꿔야 하면 세트의 `"scoring": { "lossCapRatio": 0.5 }`로 조정한다.
4. **획득 한도는 두지 않는다.** 문제마다 `points`가 곧 그 문제의 최대 획득 점수다.
5. `timeLimit`은 제출 마감으로만 쓴다. 응답 시간은 **동점자 순위 결정**에만 쓴다 (누적 응답 시간이 짧은 쪽이 위).

**정오답이 아닌 모드의 처리**

| 모드 | 방식 |
|---|---|
| `reaction` (반응속도) | 순위별 고정 점수 `"rankPoints": [300, 200, 100]`, 그 외 유효 반응자는 `points` |
| `long_typing` (장문) | 정확도 기준 통과 시 `points` — `"passAccuracy": 0.9` |
| `emoji_find` | 찾을 때마다 `points` |

**부가 사항**

- 점수 변동은 `score_events`에 `원점수 / 한도 적용 후 점수`를 함께 남겨 사후 검증에 쓴다.
- 업로드 시 JSON을 검증해 오류 위치를 관리자 화면에 보여준다 (현재는 서버 오류 메시지만 표시).
- 기존 세트(`maxScore`/`penalty`)는 `maxScore → points`로 읽어 그대로 업로드되게 하고, 변환 안내를 띄운다.
- `quiz_set_guide.md`를 새 포맷으로 다시 쓴다.

### 3.5 팀 구성 — 학년과 브릿지

지금은 참가자가 `반` 하나만 고른다 (`shared/constants.js`의 `CLASS_OPTIONS`에 고정). 개편 후에는 **학년(팀) → 브릿지(학년 안의 반)** 2단계로 소속되고, 명단은 문제 세트 JSON에 함께 넣는다.

```json
{
  "sessionName": "11월 레크레이션",
  "teams": {
    "labels": { "group": "학년", "unit": "브릿지" },
    "groups": [
      { "name": "중1", "units": ["브릿지 A", "브릿지 B"] },
      { "name": "중2", "units": ["브릿지 A", "브릿지 B", "브릿지 C"] },
      { "name": "고1", "units": ["브릿지 A"] }
    ],
    "teamScore": "adjusted"
  },
  "rounds": [ … ]
}
```

- JSON에는 **브릿지 이름만** 넣는다. 당일 누가 올지 알 수 없으므로 학생 명단은 두지 않고, 이름은 참가자가 직접 입력한다.
- **등록 화면**: 방 코드 입력 → 서버가 그 방의 명단을 내려줌 → 이름 입력 + 학년 선택 + (선택한 학년의) 브릿지 선택. 세 가지가 모두 채워져야 입장된다.
- 명단은 방에 세트를 업로드한 시점에 확정되므로, **참가자 입장 전에 세트를 올려야 한다**. 관리자 "준비" 탭에서 세트가 없으면 QR을 띄우지 않는다.
- `teams`가 없는 세트는 기존처럼 단일 소속 선택으로 동작한다 (기존 세트 호환).
- 관리자 모니터링에서 참가자의 학년·브릿지를 수정할 수 있다 (잘못 고른 경우 대비).

**팀 점수 계산 — 보정 평균 (`teamScore: "adjusted"`, 기본)**

브릿지마다 당일 출석 인원이 다르므로 인원 차이를 보정해야 한다. 단순한 방식은 둘 다 문제가 있다.

- **합계**: 인원 많은 브릿지가 무조건 유리하다.
- **단순 평균**: 1–2명만 온 브릿지가 잘하는 한 명 덕에 1위를 하거나, 중간에 나간 한 명 때문에 평균이 크게 떨어진다.

그래서 **각 브릿지에 "전체 평균 점수를 받은 가상의 참가자 3명"을 더해서 평균**을 낸다.

```
브릿지 점수 = (브릿지원 점수 합 + 3 × 전체 평균) ÷ (브릿지 인원 + 3)
```

| 브릿지 | 인원 | 단순 평균 | 보정 평균 (전체 평균 800) |
|---|---|---|---|
| A | 2명 | 1,400 | (2,800 + 2,400) ÷ 5 = **1,040** |
| B | 8명 | 1,150 | (9,200 + 2,400) ÷ 11 = **1,055** |

- 인원이 적을수록 전체 평균 쪽으로 당겨지고, 인원이 많을수록 실제 평균에 가까워진다. 위 예에서 단순 평균은 A가 이기지만, 8명이 고르게 잘한 B가 1위가 된다.
- 소수 브릿지도 잘하면 여전히 상위권에 오른다 (A는 전체 평균 800보다 훨씬 높은 1,040).
- **한 번도 답을 제출하지 않은 참가자는 계산에서 뺀다** — 등록만 하고 나간 사람이 브릿지 평균을 깎지 않게 한다.
- 가상 인원 수 3은 `"teamScoreWeight": 3`으로 조정한다. 브릿지 평균 인원의 절반 정도가 적당하다 (0이면 단순 평균과 같다).
- 시상 화면에는 보정 점수와 함께 인원수를 표시한다. 계산식은 관리자 화면에서 볼 수 있게 해, 결과에 질문이 나와도 설명할 수 있게 한다.
- 다른 방식이 필요하면 `average`(단순 평균) / `sum`(합계)으로 바꿀 수 있다.

- 학년 점수와 브릿지 점수는 같은 방식으로 각각 계산한다. 브릿지 이름이 학년마다 겹쳐도 되도록 내부 키는 `학년/브릿지`로 둔다.

### 3.6 최종 시상 — 시상 세트

지금은 시상 항목(1등, 중간, 31등, 최단 응답, 최다 채팅, 랜덤, 반별 순위)과 보여주는 방식이 코드에 고정돼 있다 (`server/gameEngine.js`의 `computeAwardsFromSession`, AdminPage 시상 탭). 이를 **시상 세트**로 바꿔 JSON에서 항목·순서·연출을 지정한다. 아래는 **이번 행사 세트**다.

```json
"awards": {
  "items": [
    { "type": "unit_ranking", "title": "브릿지 순위", "reveal": "countup" },
    { "type": "random", "title": "행운상", "reveal": "slot", "count": 3 },
    { "type": "individual_ranking", "title": "개인 순위", "reveal": "countup", "top": 5 },
    { "type": "special", "metric": "middle", "title": "뉴평 중간값", "reveal": "card" }
  ]
}
```

- 브릿지 순위: 보정 평균(3.5) 기준, 하위부터 한 줄씩 공개.
- 행운상: 전체 참가자 중 3명 추첨, 한 명씩 슬롯으로 공개 (중복 당첨 없음).
- 개인 순위: 5위 → 1위 순으로 공개.
- 뉴평 중간값: 개인 순위의 정중앙에 있는 참가자 1명 (참가자가 짝수면 위쪽 순위).

**시상 항목 종류 (`type`)**

| type | 내용 |
|---|---|
| `individual_ranking` | 개인 순위 상위 N명. `scope`로 전체 / 학년 내 / 브릿지 내 지정 |
| `group_ranking` | 학년 순위 |
| `unit_ranking` | 브릿지 순위. `scope: "group"`이면 학년별로 나눠서 표시 |
| `special` | 특별상 — `metric`: `rank`(지정 등수) · `middle`(정중앙) · `fastest`(평균 응답 최단) · `chattiest`(채팅 최다) · `round_best`(특정 라운드 1위) |
| `random` | 추첨. `count`명, `scope`로 대상 범위 지정 |

**보여주는 방식 (`reveal`)**

| reveal | 연출 |
|---|---|
| `podium` | 3등 → 2등 → 1등 순서로 단상에 한 명씩 등장 |
| `countup` | 하위부터 한 줄씩 위로 쌓으며 공개 |
| `bar_race` | 팀별 막대가 동시에 차오르며 순위 확정 |
| `card` | 수상자 한 명을 카드로 크게 공개 (현재 방식) |
| `slot` | 슬롯머신 추첨 (현재 방식) |
| `scroll` | 전체 목록 자동 스크롤 (3.2의 집계 화면 재사용) |

- 항목마다 `reveal`을 따로 줄 수 있고, 생략하면 type별 기본 연출을 쓴다.
- `awards`를 생략하면 이번 행사 세트를 기본으로 쓴다. 다른 구성은 `"preset"`으로 고른다: `team_only`(팀 순위만) / `quick`(개인 상위 3명만).
- 관리자 시상 탭에서 세트를 불러온 뒤 **순서 변경·항목 끄기·연출 변경**을 당일에 할 수 있다.
- 진행은 리모트의 주 버튼으로 한다: `다음 시상 항목` → `한 단계 공개`(podium의 3등→2등→1등 등) → `다음 시상 항목`. 진행자 화면에는 공개 전에 결과가 미리 보인다.
- 수상 결과는 게임 종료 시점에 한 번 계산해 저장한다. 추첨(`random`)만 공개 시점에 서버가 뽑는다 (현재는 관리자 브라우저에서 뽑음).

## 7. 리허설 피드백 (2026-11-12)

리허설은 정상 작동. 받은 피드백은 모두 행사 전에 바로 반영했다 — 작고, 행사 진행 방식과 공정성에 직접 닿는 내용이라 미룰 이유가 없었다.

| 피드백 | 판단 | 반영 내용 |
|---|---|---|
| 참가자: 제출 시 정답·오답과 정답을 공개하지 않고, 고른 답만 눌린 채 대기 | 지금 | 화면뿐 아니라 **서버가 정답 공개 전까지 결과를 보내지 않게** 바꿨다. 화면만 가리면 폰이 받은 데이터에 결과가 남는다. 이번 문제 점수도 공개 전에는 반영하지 않고 보여준다. 새로고침해도 고른 답이 유지된다 |
| 참가자: 정답 공개 때 얻은 점수 플로팅 | 지금 | 공개 순간 `+100` / `-50` / `0`과 `정답!`·`오답`·`미제출`이 떠올랐다 사라진다 |
| Display: 보기 글씨가 작음 | 지금 | 오른쪽 타이머 영역을 없앤 만큼 보기 글씨를 약 1.6배로 키웠다 |
| Display: 카운트를 오른쪽 위 작은 초시계로, 제출 수도 축소 | 지금 | 오른쪽 위에 초시계 모양 타이머와 작은 제출 수 막대 |
| Display: 정답 공개 시 큰 카드로 정답 플로팅 | 지금 | 문제와 보기 사이(이미지가 있으면 이미지 위)에 큰 정답 카드가 떠오른다. 정답 인원 표시 포함 |

함께 바꾼 것: 정답 공개 전(접수 마감 단계 포함)에는 개인 집계를 띄울 수 없다. 집계 점수로 정답이 드러나기 때문이다.

## 8. 점수 단위 변경 (2026-11-13)

요청: 문제당 100–200점씩 쌓이던 점수를 5점, 3점처럼 작게. 기존 세트는 비율로 환산.

판단: **지금 적용**. 행사용 문제 세트를 만들기 전에 단위가 정해져야 하고, 서버·화면은 점수 값을 그대로 쓰는 구조라 변경 범위가 작다.

| 항목 | 내용 |
|---|---|
| 기본 점수 | 100점 → 5점 (감점 기본 0점 유지) |
| 기존 큰 단위 세트 | 업로드 때 가장 많이 쓰인 문제 점수를 5점에 맞춰 비율 환산. 100 → 5, 300 → 15, 감점 50 → 3, 반응속도 300/200/100 → 15/10/5. 0이 아닌 값은 최소 1점 |
| 이미 작은 단위인 세트 | 기준 점수가 10점 이하면 환산하지 않음 |
| 조절 | `scoring.scaleTo`(기준 점수, 기본 5), `scoring.autoScale: false`(환산 끄기) |
| 팀 점수 | 점수가 작아 정수 반올림 시 동점처럼 보이므로 소수 첫째 자리까지 |
| 손실 한도 | 규칙 그대로 (라운드 감점 합의 50%) — 환산된 점수 기준으로 계산 |

## 9. 정답 참고 이미지 (2026-11-13)

요청: 정답 발표 때 참고 사진을 보여주는 옵션 (예: 정답 서울 → 서울 사진). 세트에 경로를 지정하면 불러온다. 정답 카드는 문제·보기의 80%를 가릴 만큼 키워도 됨.

판단: **지금 적용**. 행사용 세트를 만들 때 바로 쓰는 옵션이고, 정답 공개 화면만 바뀐다.

| 항목 | 내용 |
|---|---|
| 세트 옵션 | 문제에 `answerImage`(파일명 또는 https 주소), `answerNote`(한 줄 설명) |
| Display | 정답 카드를 화면 폭 84%·상단 머리줄 아래 전체 높이로 키움. 사진이 있으면 왼쪽에 크게, 오른쪽에 정답·설명·정답 인원 |
| 참가자 폰 | 정답 공개 때 같은 사진·설명을 보기 아래에 표시 |
| 보안 | 사진·설명은 공개 순간에만 전송 (Display 는 누구나 열 수 있으므로) |
| 사진 올리기 | 관리자 ① 준비 탭에 "문제·정답 이미지" — 올리고 주소 복사 (Supabase Storage) |

## 10. 문제 만들기 화면 (2026-11-13)

요청: JSON을 직접 쓰지 않도록, 관리자 페이지에 게임별로 입력하는 문제 만들기 화면을 두고 JSON으로 내보내기.

판단: **지금 적용**. 행사 전에 세트를 만들어야 하고, 손으로 쓰는 JSON은 오타·형식 오류가 잦다. 서버 변경 없이 관리자 화면만 추가하면 된다.

| 항목 | 내용 |
|---|---|
| 위치 | 관리자 **⑤ 문제 만들기** 탭. 방이 없어도 열린다 |
| 입력 | 기본 정보(행사 이름·기본 점수·시상 구성), 학년·브릿지, 라운드별 게임 모드 → 모드에 맞는 칸만 표시 (보기+정답 체크, 초성 자동, 이미지·오디오 주소와 미리보기, 원문, 이모지 설정, 반응속도 순위 점수, 정답 사진·설명) |
| 편집 | 라운드·문제 추가·복제·삭제·순서 이동, 게임 모드 변경 시 공통 내용 유지 |
| 검사 | 서버와 같은 검사기를 브라우저에서 실행. 오류 난 문제·라운드에 표시, 경고는 R·Q 번호와 함께 |
| 저장 | 브라우저에 자동 저장 (창을 닫을 때도 즉시 저장) |
| 내보내기·불러오기 | JSON 파일로 내보내기, 기존 JSON 불러오기 (기존 형식·큰 점수 단위는 새 형식·5점 단위로 바꿔서 불러옴) |
| 방에 적용 | 열려 있는 방(입장 대기 중)에 바로 적용 |
| 사진 | "올린 이미지" 버튼으로 ① 준비 탭에서 올린 사진을 골라 넣기 |

## 11. 직접 입력 답 채점 — 띄어쓰기 무시, 복수 정답 (2026-11-13)

요청: 단답형처럼 타이핑으로 내는 답은 띄어쓰기나 부르는 방법에 따라 여러 가지가 될 수 있으니, 띄어쓰기와 상관없이 인정하고 복수 정답을 처리.

판단: **지금 적용**. 행사에서 바로 쓰는 모드이고, 맞는 답이 오답 처리되면 공정성 문제가 된다.

| 항목 | 내용 |
|---|---|
| 띄어쓰기·대소문자 | 원래부터 무시하고 있었음 (변경 없음) |
| 문장부호 | 새로 무시: `. , ! ? ~ ' " · - ( )` 등, 전각 문자는 반각으로 |
| 복수 정답 | 문제에 `acceptAnswers` (다른 인정 답 목록). `correctAnswer`를 배열로 적어도 됨 |
| 적용 모드 | 단답형·초성·빈칸·이미지 퀴즈·오디오 퀴즈. 객관식은 보기를 그대로 비교 (영향 없음) |
| 화면 | 정답 공개 카드에 "또는 …", 참가자 폰에 "정답: A / B", 진행자 화면·순서표에 인정 답 |
| 문제 만들기 | 정답 칸 아래 "다른 인정 답" 입력 |
