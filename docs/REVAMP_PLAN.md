# NewCreation 종합 개편 플랜 (v2)

> 상태: 초안 · 작성일 2026-11-11
> 범위: 진행자 리모트 추가, 중간 개인 집계, 관리자 표시 설정, 포인트 체계 간소화

## 1. 개편 방향 요약

기존 3-way 구조(참가자 폰 · 관리자 PC · 프로젝터 Display)에 **진행자 리모트**를 더해 4-way 구조로 간다.

| 화면 | 경로 | 기기 | 역할 |
|---|---|---|---|
| 참가자 | `/` `/lobby` `/game` | 개인 폰 | 답안 입력, 채팅, 내 점수·순위 확인 |
| Display | `/display` | 프로젝터 | 문제·타이머·집계·시상 송출 |
| 관리자 | `/admin` | PC (음향/방송석) | 방 생성, 문제 세트 업로드, 표시 설정, 모니터링, 시상 |
| **진행자 리모트 (신규)** | `/host` | 진행자 폰 (강단) | 게임 순서 진행, 정답 공개, 집계 송출 |

기술 스택(React 18 + Vite + Tailwind + Zustand / Express + Socket.io / Supabase)은 유지한다.
게임 모드 컴포넌트 11종은 재사용하고, **서버 진행 로직 · 점수 엔진 · 관리자/Display 페이지**는 새로 짠다.

### 지금 구조에서 개편 때 같이 정리할 문제

현재 코드를 읽으며 확인한 것들로, 신규 요구사항과 직접 얽혀 있어 함께 처리한다.

- **관리자 비밀번호가 클라이언트 번들에 포함됨** — `VITE_ADMIN_PASSWORD`가 빌드 결과물에 그대로 들어가 누구나 볼 수 있다 (`client/src/pages/AdminPage.jsx:6`). 진행자 기기가 추가되므로 서버 발급 토큰 방식으로 바꾼다.
- **진행 상태가 서버 메모리에만 있음** — Railway 재시작 시 진행 중인 방이 사라진다 (`server/gameEngine.js`).
- **진행 명령에 순서 보호가 없음** — `admin:next_question`이 중복 수신되면 문제가 건너뛰어진다. 관리자 PC와 진행자 폰 두 곳에서 조작하게 되면 더 자주 발생한다.
- **채팅 로그가 세션과 연결되지 않음** — `session_id: null`로 저장된다 (`server/chatHandler.js:22`).
- **채팅 폰트 크기가 서버에서 난수로 결정됨** — 조절하려면 구조를 바꿔야 한다 (`server/chatHandler.js:8`).
- **Display 색상·폰트가 하드코딩** — 테마 선택을 하려면 토큰화가 필요하다 (`client/src/pages/DisplayPage.jsx`).
- **페이지가 단일 파일에 몰려 있음** — AdminPage 786줄, DisplayPage 669줄.

## 2. 핵심 설계

### 2.1 서버: 단일 상태 머신 + 역할별 상태 전송

방(room)마다 하나의 진행 상태를 서버가 소유하고, 모든 화면은 그 상태를 받아 그리기만 한다.

```
lobby → round_intro → question_open → question_closed(정답 공개)
                           ↑                  ↓
                           └──── 다음 문제 ────┤
                                              ↓
                     standings(개인 집계) ⇄ round_end → … → final → awards
```

- 서버는 상태가 바뀔 때마다 `room:state` 스냅샷을 내보내되, **역할에 따라 내용을 다르게** 보낸다.
  - 참가자: 정답 제외, 본인 점수·순위만
  - Display: 문제·타이머·제출 현황·집계
  - 진행자/관리자: 정답, 다음 순서 미리보기, 제출 현황, 접속자 수
- 재접속 시 같은 스냅샷 한 번으로 화면이 복구된다 (현재의 이벤트별 개별 복구 로직 제거).
- 타이머는 매초 tick 이벤트 대신 **마감 시각(`deadlineAt`)** 을 한 번 보내고 각 화면이 계산한다. 서버가 마감만 판정한다.
- 상태 스냅샷은 전환 시점마다 Supabase에 저장해, 서버가 재시작돼도 방을 복구한다.

### 2.2 진행 명령과 중복 방지

진행자와 관리자는 같은 명령 채널을 쓴다.

```js
socket.emit('host:command', { type: 'next', step: 17 })
```

- `step`은 현재 진행 단계 번호. 서버의 현재 값과 다르면 명령을 무시한다 → 더블 탭이나 두 기기 동시 조작으로 문제가 건너뛰어지지 않는다.
- 명령 종류: `next` `reveal` `show_standings` `hide_standings` `pause` `resume` `extend_time` `skip` `goto` `end_game`

### 2.3 인증

- `/admin` 로그인: 비밀번호를 서버로 보내 검증 → 서명된 토큰 발급 (role: admin). 클라이언트 번들에 비밀번호를 두지 않는다.
- `/host` 접속: 관리자 화면이 방마다 **진행자용 QR/링크**를 발급 (role: host, 해당 방 한정). 진행자는 비밀번호 입력 없이 QR로 들어온다.
- 모든 소켓은 연결 시 토큰으로 역할을 확정하고, 이후 이벤트마다 비밀번호를 싣는 현재 방식은 없앤다.

| 권한 | admin | host |
|---|---|---|
| 방 생성/종료, 문제 세트 업로드 | ✅ | — |
| 진행 명령 (다음/공개/집계/일시정지) | ✅ | ✅ |
| 표시 설정 (폰트/테마) | ✅ | — |
| 시상 송출 | ✅ | ✅ |

## 3. 요구사항별 설계

### 3.1 진행자 리모트 UI (`/host`)

강단에서 한 손으로, 화면을 오래 보지 않고 조작하는 것을 기준으로 한다.

```
┌──────────────────────────┐
│ R2 초성 퀴즈 · 3/8   ● 연결됨 │  ← 현재 위치, 연결 상태
├──────────────────────────┤
│ 문제: ㅂㄷㄹㅎ              │
│ 정답: 베들레헴              │  ← 진행자에게만 보임
│ ⏱ 12초   제출 34/41       │
├──────────────────────────┤
│                          │
│      [   정답 공개   ]     │  ← 주 버튼 1개, 상황에 따라 라벨 변경
│                          │
├──────────────────────────┤
│ 다음: 문제 4 "ㅇㄹㅅㄹ"      │  ← 다음 순서 미리보기
├──────────────────────────┤
│ [개인 집계] [일시정지] [⋯]   │  ← 보조 동작
└──────────────────────────┘
```

- **주 버튼 하나**가 현재 단계에 맞는 다음 동작을 수행한다: 게임 시작 → 문제 시작 → 정답 공개 → 다음 문제 → 라운드 결과 → 다음 라운드.
- 보조 동작: 개인 집계 송출/닫기, 일시정지, 시간 연장(+10초), 문제 건너뛰기, 순서표에서 특정 문제로 이동.
- 건너뛰기·게임 종료 같은 되돌릴 수 없는 동작은 확인 단계를 둔다.
- 화면 꺼짐 방지(Wake Lock), 연결 끊김 시 화면 상단 경고 + 자동 재접속 후 상태 복구.
- 관리자 PC의 진행 패널도 같은 컴포넌트를 써서, 진행자 폰이 없어도 PC만으로 진행할 수 있다.

### 3.2 게임 중간 개인 집계

- **송출 시점**: 진행자가 문제 사이 언제든 `개인 집계` 버튼으로 띄우고 닫는다. JSON에서 라운드에 `"standingsAfter": true`를 주면 라운드 종료 시 자동으로 띄운다.
- **Display**: 전체 참가자를 순위순으로 나열하고 **자동 스크롤**한다.
  - 상위 3명은 상단 고정, 4위부터 아래 영역에서 스크롤
  - 끝까지 가면 잠시 멈춘 뒤 처음으로 돌아가 반복
  - 스크롤 속도는 인원수에 비례해 자동 계산 (한 줄당 표시 시간 고정), 관리자 설정에서 배속 조절
  - 각 줄: 순위 · 이름(반) · 누적 점수 · 직전 집계 대비 증감 · 순위 변동(▲▼)
- **참가자 폰**: 집계가 떠 있는 동안 본인 순위·점수·증감을 크게 보여준다.
- **집계 범위**: 누적(기본) / 이번 라운드만 — 진행자가 전환.
- 서버는 집계 송출 시점의 점수를 기록해 다음 집계의 증감·순위 변동 계산에 쓴다.

### 3.3 관리자 페이지 — 표시 설정

`/admin`을 탭으로 재구성한다: **준비**(방·문제 세트·진행자 QR) / **진행**(리모트와 동일 패널 + 모니터링) / **표시 설정** / **시상**.

표시 설정은 방 상태에 `displaySettings`로 저장하고, 바꾸는 즉시 Display에 반영한다.

| 설정 | 조작 | 비고 |
|---|---|---|
| 채팅 폰트 크기 | 슬라이더 (50%–300%) | Display에서 CSS 변수로 배율 적용. 서버 난수 크기는 제거하고 메시지별 편차만 클라이언트에서 소폭 부여 |
| 채팅 표시 | 켜기/끄기, 투명도, 흐르는 속도 | 문제 풀이 중 자동 숨김 옵션 |
| 테마 | 프리셋 선택 (다크 네온 / 파스텔 / 라이트 등) | 색·폰트를 CSS 변수 토큰으로 정의 |
| 배경 | 단색 / 그라디언트 / 이미지 / 영상 | `client/public/media/` 파일 또는 URL 지정 |
| 집계 스크롤 속도 | 0.5×–2× | |

- 설정 화면에 Display 미리보기를 축소해 넣어, 프로젝터를 보지 않고도 확인할 수 있게 한다.
- 설정은 세션에 저장되며, "기본값으로 저장"으로 다음 방에도 이어 쓸 수 있다.
- JSON 문제 세트에서 `"display": { "theme": "pastel", "background": "/media/bg.jpg" }`로 초기값을 줄 수 있다.

### 3.4 포인트 간소화

**변경 전**: `maxScore × (0.3 + 남은시간비율 × 0.7)`, 오답도 시간 비례 감점 (`server/scoringEngine.js`).
**변경 후**: 시간은 점수에 영향을 주지 않는다. 맞으면 지정 점수, 틀리면 지정 감점. 구간(라운드)마다 획득·손실 한도를 둔다.

```json
{
  "sessionName": "11월 레크레이션",
  "scoring": { "points": 100, "penalty": 0 },
  "rounds": [
    {
      "roundNumber": 1,
      "theme": "성경 상식",
      "gameMode": "multiple_choice",
      "points": 100,
      "penalty": 50,
      "maxGain": 500,
      "maxLoss": 200,
      "standingsAfter": true,
      "questions": [
        { "content": "…", "choices": ["…"], "correctAnswer": "…", "timeLimit": 15 },
        { "content": "보너스 문제", "choices": ["…"], "correctAnswer": "…", "points": 300 }
      ]
    }
  ]
}
```

**규칙**

1. 점수 값은 `문제 → 라운드 → 세트(scoring) → 기본값(100 / 0)` 순으로 찾는다.
2. 정답 `+points`, 오답 `-penalty`, 미제출 0점.
3. 한 참가자가 한 구간(라운드)에서 얻는 합계는 `+maxGain`을, 잃는 합계는 `-maxLoss`를 넘지 않는다. 한도를 넘는 부분은 반영하지 않는다. 생략하면 한도 없음.
4. `timeLimit`은 제출 마감으로만 쓴다. 응답 시간은 **동점자 순위 결정**에만 쓴다 (누적 응답 시간이 짧은 쪽이 위).

**정오답이 아닌 모드의 처리**

| 모드 | 방식 |
|---|---|
| `reaction` (반응속도) | 순위별 고정 점수 `"rankPoints": [300, 200, 100]`, 그 외 유효 반응자는 `points` |
| `long_typing` (장문) | 정확도 기준 통과 시 `points` — `"passAccuracy": 0.9` |
| `emoji_find` | 찾을 때마다 `points`, 라운드 `maxGain`으로 상한 |

**부가 사항**

- 점수 변동은 `score_events`에 `원점수 / 한도 적용 후 점수`를 함께 남겨, 집계 증감 계산과 사후 검증에 쓴다.
- 업로드 시 JSON을 검증해 오류 위치를 관리자 화면에 보여준다 (현재는 서버 오류 메시지만 표시).
- 기존 세트(`maxScore`/`penalty`)는 `maxScore → points`로 읽어 그대로 업로드되게 하고, 변환 안내를 띄운다.
- `quiz_set_guide.md`를 새 포맷으로 다시 쓴다.

## 4. 데이터 모델

문제는 세션 단위로만 쓰이므로 `rounds`/`questions` 테이블을 없애고 세트 JSON을 통째로 저장한다.

| 테이블 | 주요 컬럼 | 변경 |
|---|---|---|
| `sessions` | `room_code`, `status`, `quiz_set jsonb`, `settings jsonb`, `state jsonb` | 컬럼 추가 |
| `players` | `session_id`, `name`, `class_name`, `score`, `total_response_ms` | 컬럼 추가 |
| `score_events` | `player_id`, `round_idx`, `question_idx`, `answer`, `is_correct`, `raw_delta`, `applied_delta`, `response_ms` | `answers` 대체 |
| `chat_logs` | `session_id`, `player_id`, `message` | session_id 실제 기록 |

기존 데이터는 보존할 필요가 없으면 새 스키마로 교체한다 (→ 6장 확인 사항).

## 5. 단계별 진행

각 단계는 로컬에서 4개 화면을 띄워 확인할 수 있는 상태로 끝낸다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **0. 기반** | 공용 프로토콜(`shared/`) 정의, 스키마 v2, 테스트 환경(Vitest), 폴더 구조 정리 | 상태·명령·JSON 포맷이 문서와 타입으로 확정 |
| **1. 서버 코어** | 상태 머신, 점수 엔진 v2(한도 포함), 토큰 인증, 상태 저장·복구 | 점수·상태 전환 단위 테스트 통과, 서버 재시작 후 방 복구 |
| **2. 진행자 리모트 + 관리자** | `/host` 신규, `/admin` 탭 재구성, 진행자 QR, JSON 검증 | 폰 하나로 세트 전체를 끝까지 진행, 두 기기 동시 조작에도 건너뛰기 없음 |
| **3. Display** | 테마 토큰화, 표시 설정 실시간 반영, 개인 집계 자동 스크롤, 채팅 폰트 조절 | 관리자에서 바꾼 설정이 즉시 반영, 100명 집계가 끊김 없이 스크롤 |
| **4. 참가자** | 새 상태 프로토콜로 전환, 11개 모드 이식, 내 순위 화면 | 모든 모드가 새 점수 규칙으로 동작, 재접속 복구 |
| **5. 배포·리허설** | Vercel/Railway 재연결, 환경변수 정리, 가상 참가자 부하 테스트, 실기기 리허설 | 실제 기기 4종으로 샘플 세트 완주 |

**배포**: 1–4단계는 로컬 개발로 진행하고, 5단계에서 Vercel(client)·Railway(server)를 재연결한다. `vercel.json`과 `Dockerfile`은 그대로 쓸 수 있다. 바뀌는 환경변수는 `VITE_ADMIN_PASSWORD` 삭제, 서버에 `TOKEN_SECRET` 추가.

```
  store/     roomStore.js(스냅샷 단일 스토어)
```

## 6. 확인이 필요한 사항

진행 전에 정해져야 하는 것들이다. 답이 없으면 **기본안**으로 진행한다.

1. **"구간별 최대 포인트 획득/손실"의 구간** — 기본안: 구간 = 라운드, 참가자 1인의 라운드 내 누적 획득·손실에 한도 적용. (다른 해석: 여러 라운드를 묶은 파트 단위, 또는 한 문제 안의 점수 단계)
2. **개인 집계에 전원 표시 여부** — 기본안: 전원 표시. 하위권 노출이 부담되면 "상위 N명 + 본인 순위는 폰에서만" 옵션을 둔다.
3. **진행자 리모트 권한 범위** — 기본안: 진행 명령과 시상 송출만. 표시 설정·방 종료는 관리자 PC 전용.
4. **기존 DB 데이터** — 기본안: 보존하지 않고 새 스키마로 교체.
5. **동시 참가 인원 규모** — 기본안: 100명 기준으로 부하 테스트.
6. **배경 이미지/영상 관리 방식** — 기본안: 리포의 `client/public/media/`에 넣고 선택. 행사 당일 업로드가 필요하면 Supabase Storage 연동을 추가한다.
